# OCI 镜像 Squash 工具技术方案

> 基于对两个参考仓库的调研,给出用 Go 实现、原生支持 OCI 的镜像 squash(层压缩/合并)工具的完整技术方案。

- 参考项目 1:`/home/liang/.aworks/goworks/docker-squash`(jwilder/docker-squash,Go,已停止维护,不适配 OCI)
- 参考项目 2:`/home/liang/.aworks/pyworks/docker-squash`(goldmann/docker-squash,Python,功能完整但压缩耗时长)

---

## 〇、核心设计原则:压缩耗时是第一优先级

本工具目的是**合并镜像层**——N 层合并后必然产出 1 个新层并压缩它。在正确性之外,**压缩是唯一无法回避、且量级最大的耗时**,因此全案以"压缩耗时最小"为第一约束,其余为它让路。三条推论贯穿全文:

1. **只压该压的**:N 层合并成 1 层,只有这 1 个合并层需要压缩;被保留的下层(move)直接复用原压缩 blob,绝不重压(§4.2-A)。
2. **压缩必须并行,且绝不交给 ggcr**:ggcr 内置压缩走标准库 `compress/gzip`,**单线程、基本只支持 gzip**。压缩耗时优先意味着必须用 `klauspost/compress` 自己并行压,再把"已压好的 blob + 已算好的 digest/diff_id"交给 ggcr 组装 manifest(§3.6、§4.4)。**这是路线 A 最容易踩、且直接决定成败的点。**
3. **压缩与其余阶段重叠,算法/级别可选**:压缩与解压合并流水线重叠(墙钟 ≈ max(合并, 压缩));默认选吞吐最高的 zstd,并暴露级别与 `none`,让用户在"快"与"小"之间选(§3.6、§4.2)。

> 由此得到一个反直觉但重要的结论:**压缩耗时几乎与"选路线 A 还是 B"无关**(两条路线都自己并行压),真正决定它的是压缩器、算法、级别、核数(§4.4)。

## 一、调研结论:两个参考项目的价值与短板

### 1.1 jwilder/docker-squash (Go, EOL)

全部逻辑约 700 行,单 `package main`,无 go modules(用 `GLOCKFILE` 管理依赖)。

**可借鉴的算法骨架:**

- 分层"叠加合并"思路:把层依次铺到一个目录,再重新打包成一层
- whiteout 删除逻辑(`.wh.` 前缀标记)
- 层分类思想:纯元数据层(ENV/CMD/EXPOSE 等 `#(nop)` 且非 ADD/COPY)保留,文件系统层折叠进 squash 层
- `Export`(层图)与 `ExportedImage`(磁盘上的单层)的职责分离

**不能直接用的部分(几乎是整个 IO/格式层):**

- 只认 Docker v1 legacy 格式(每层一个以层 ID 命名的目录,内含 `json` / `VERSION`("1.0") / `layer.tar`,顶层 `repositories` 文件),**完全没有 OCI 概念** —— 无 `oci-layout`、无 `index.json`、无 `manifest.json`、无内容寻址的 `blobs/sha256/`、无 config digest
- 层顺序靠 `parent` 字段串成链表,而非 OCI 的有序 `layers[]` 数组 + `rootfs.diff_ids`
- 用随机 256-bit hex 作层 ID,而非内容寻址,**从不计算任何 hash**(没有 diff_id / digest)
- **不做任何压缩**,只处理未压缩 `layer.tar`
- 靠 shell 调用系统 `tar`(`--overwrite` 叠加解包),多处还要 `sudo`,要求 root + GNU tar 1.27
- 用字符串匹配容器配置 `Cmd` 中的 `#(nop) ADD file` / `#(squash)` 判断层类型 —— BuildKit 已不产出 `#(nop)` 格式,启发式失效
- 只处理 AUFS `.wh.<name>`,**不处理 OCI/overlayfs 的 opaque 目录标记 `.wh..wh..opq`**(会被当成删除名为 `.opq` 的文件,行为错误)

### 1.2 goldmann/docker-squash (Python, 慢)

核心逻辑在 `image.py`(~1037 行,格式无关算法)与 `v2_image.py`(Docker Schema v2 / OCI 的 manifest+config 处理)。**已支持 OCI archive**(检测 `index.json` 置 `oci_format=True`)。

**必须忠实复刻的正确性细节:**

- **newest-first 合并**:从最新层往老层遍历,已见过的路径跳过老副本(实现"后写胜出",且能让最终 tar 更轻)
- **whiteout 完整语义:**
  - 普通 `.wh.<name>`:squash 范围内标记 + 目标都丢弃;**若被删目标位于"移动"(保留的下层)里,必须重新发射 whiteout 标记**,否则下层文件不会被隐藏
  - opaque 目录 `.wh..wh..opq`:记录该目录,遮蔽更老层中该目录下的所有内容
  - **marker reduction(`_reduce`)**:祖先目录已有 marker 覆盖时,删除子路径的冗余 marker —— 注释明确说明这不是优化,冗余 marker 会让 Docker **加载失败**
  - AUFS 上的 marker 可能是硬链接,需重建成普通文件
- **符号链接/硬链接延后处理**(先跳过,末尾回填;允许 broken symlink,运行时可能经 volume 解析)
- **路径归一化** `os.path.normpath(os.path.join("/", path))`:消除 `./` 前缀与裸路径的不一致
- **config 重算(V2):**
  - `diff_id` = 每层**未压缩** tar 的 sha256
  - `chain_id` = 递归 `sha256("sha256:<parent> sha256:<diff>")`
  - image config:克隆旧 config(用 OrderedDict 保序以字节对齐 hash),更新 `created`,删 `container`/`container_config`,`history` 截断到 moved 层数并追加 1 条新条目(全空时 `empty_layer:true`),`rootfs.diff_ids` 截断并追加
  - image ID = config JSON(紧凑分隔符 + 末尾换行)的 sha256
  - 甚至用正则修剪微秒以匹配 Go 的日期序列化,做到与 Docker 字节一致

**性能瓶颈(要规避的):**

1. **整个镜像全量解包到磁盘**(`docker save` 流 → 落盘到 `old/`)
2. **每个文件的字节都过 Python `tarfile` 拷贝**(`extractfile` → `addfile`,`copyfileobj`)—— 主要开销,O(总字节数),GIL 无并行
3. `getmembers()` 对每层解析整份头索引到内存
4. `squashed_files` / `to_skip` 用 **list** 做子串/前缀线性查找,最坏 **O(files²)**
5. 结尾**多次全量重打包 + 多次独立 hash pass**(export tar、load tar、compute_sha256 各扫一遍)
6. **全程单线程**(仅 save 时一个 pipe 读线程)

> 关键洞察:Python 版**根本没做压缩**(全程未压缩 tar)。所谓"压缩耗时长"其实是 tar 重处理 + Python 逐字节 IO + daemon 侧串行。Go 版既能在合并路径上快数量级,还能额外叠加真正的并行压缩。

## 二、总体架构

```
oci-squash/
├── cmd/oci-squash/main.go        # CLI 入口 (cobra)
├── internal/
│   ├── oci/                      # OCI 格式层:读写 image layout / tar
│   │   ├── layout.go             #   oci-layout, index.json, blobs/sha256/
│   │   ├── manifest.go           #   manifest + config 解析/生成
│   │   └── source.go             #   来源抽象:OCI dir / OCI tar / docker-archive / registry
│   ├── squash/                   # 核心算法(格式无关)
│   │   ├── squash.go             #   编排:选层→合并→重算→写出
│   │   ├── merge.go              #   newest-first 合并 + 去重
│   │   ├── whiteout.go           #   whiteout / opaque / marker-reduce
│   │   └── config.go             #   diff_id / chain_id / history / rootfs 重算
│   ├── tarx/                     # 流式 tar 读写工具
│   └── compress/                 # 并行 gzip / zstd
└── go.mod
```

### 2.1 依赖选型(不 shell out、不 sudo、不落盘)

| 用途 | 选型 | 说明 |
|---|---|---|
| OCI/Docker 镜像读写抽象 | `github.com/google/go-containerregistry` (ggcr) | `v1.Image` / `mutate` / `tarball` / `layout` / `remote`,**只用来读来源、组装/写 manifest+config+layout**,**不用它压缩、不用它算合并层的 hash**(见下)|
| 压缩(**性能核心**) | `github.com/klauspost/compress` | 并行 gzip(pgzip)+ zstd,比标准库 `compress/gzip` 快数倍;合并层的压缩必须走这里,不能用 ggcr 内置的单线程 gzip |
| tar | `archive/tar`(标准库) | 流式读写 |
| 并行 | `golang.org/x/sync/errgroup` | 并行读层 / hash |
| CLI | `github.com/spf13/cobra` | 子命令与 flag |

### 2.2 两条实现路线

核心难点(层合并 + whiteout)两条路线都要自己写;差别只在**格式/config 由库扛还是自己扛**。

| | 路线 A:基于 ggcr `mutate`(**推荐主线**) | 路线 B:完全自研合并引擎 |
|---|---|---|
| 做法 | ggcr 读镜像;**自己并行压缩合并层、自己算 diff_id/digest**,再用预压缩 layer + `mutate` 组装 config/manifest | 自研格式层 + 合并 |
| 优点 | manifest/config 组装正确性由库保证;开发快、鲁棒;无需字节对齐 hack | 完全可控,可做极致 pipeline |
| 缺点 | 受库抽象约束;**必须绕开 ggcr 的默认压缩/hash 路径**(否则单线程压缩 + 可能压两遍,见 §4.4) | 要复刻 Python 全部正确性细节,风险高 |

建议 **A 为主线**,把"格式正确性"外包给 ggcr,精力集中在合并算法与压缩性能;B 作为后续极致优化的可选项。

> ⚠️ 无论 A/B,**合并层的压缩与 hash 都由我们自己的并行管道完成**(§3.6)。ggcr 在 A 里只负责接收"已压好的 blob"并组装 manifest/config——它不碰压缩。这样路线选择就与压缩耗时解耦了。

## 三、核心算法设计

### 3.1 输入来源抽象

```go
type Source interface {
    Image() (v1.Image, error)   // 归一为 ggcr 的 v1.Image
}
```

支持:

- OCI layout 目录(`oci-layout` + `index.json` + `blobs/sha256/`)
- OCI archive tar
- docker-archive(`docker save` 产物,含 `manifest.json`)
- (可选)registry 直接拉取

用 ggcr 后四种来源都归一为 `v1.Image`,拿到有序的 `layers []v1.Layer` 与 `configFile`,**无需像 Python 那样依赖 daemon**。

### 3.2 选层

复刻 Python `--from` 语义:

- 空 → squash 全部层
- 整数 N → squash 最后 N 层
- 层 digest / index → 从该层往上 squash

得到 `layersToMove`(底部保留)+ `layersToSquash`(合并成 1 层)。守卫:N≤0 或 N>total 报错;只有 1 层可合并时提前退出(相当于 `SquashUnnecessaryError`)。

### 3.3 合并引擎(最关键)—— newest-first + map 去重

复刻 Python 正确性,重写性能:

```go
// 伪代码:从最新层往老层遍历
squashed := map[string]struct{}{}   // 已写入路径 (map 而非 list)
skip     := newPathSet()            // 被 whiteout 命中的路径
opaque   := newPrefixSet()          // opaque 目录前缀
var deferredSym, deferredLnk []*tar.Header

for i := len(layersToSquash) - 1; i >= 0; i-- {
    tr := tar.NewReader(uncompressed(layer[i]))   // 层若压缩则流式解压
    for {
        hdr, err := tr.Next()
        // ... EOF / err 处理
        name := normalize(hdr.Name)
        switch {
        case isOpaque(hdr):         opaque.add(dir(name)); continue
        case isWhiteout(hdr):       skip.add(whiteoutTarget(name)); recordMarker(); continue
        case opaque.covers(name):   continue          // 被更新的 opaque 目录遮蔽
        case skip.has(name):        continue          // 被更新的 whiteout 遮蔽
        case seen(squashed, name):  continue          // 老副本,后写胜出
        case hdr.Typeflag == tar.TypeSymlink: deferredSym = append(deferredSym, hdr); continue
        case hdr.Typeflag == tar.TypeLink:    deferredLnk = append(deferredLnk, hdr); continue
        }
        writeHeaderAndCopy(squashedTar, hdr, tr)      // io.Copy,内核级拷贝
        squashed[name] = struct{}{}
    }
}
// 回填 hardlink / symlink(允许 broken symlink)
// 若存在 layersToMove:_reduce 精简标记后,对仍需遮蔽下层的文件重新发射 whiteout
```

相对 Python 的性能改造点:

1. **`io.Copy` 流式拷贝**代替逐字节过解释器
2. **map / 前缀树**做去重与 skip 查找,消除 O(files²)
3. **并行预索引**:多层的头解析可用 errgroup 并发;合并写出仍保持 newest-first 的确定性顺序(先并行索引,再串行写出)
4. **不落盘**:层 tar 流 → 合并 tar 流,不做全量 extract-to-disk

### 3.4 whiteout / opaque / marker-reduce

严格照搬 Python 三类处理:

- **普通 `.wh.<name>`**:squash 范围内标记 + 目标都丢弃;**若目标在 `layersToMove` 里,必须重新发射 marker**
- **opaque `.wh..wh..opq`**:记录目录,遮蔽更老层里该目录下的内容
- **marker reduction**:祖先目录已有 marker 时删掉子路径 marker(否则 Docker/containerd 加载失败),用路径层级遍历实现
- **AUFS 硬链接 marker** 重建为普通文件
- **路径归一化** `path.Clean("/" + name)`,消除 `./` 前缀不一致

> 这是移植期最大的正确性风险区,需重点测试(见第六节)。

### 3.5 config / manifest 重算

我们**自己算合并层的 diff_id/digest**(§3.6),再把这两个值喂给 ggcr 组装。语义:

- **diff_id** = 未压缩合并 tar 的 sha256(在 §3.6 的单遍管道里算出,不做二次 pass)
- **layer digest** = 压缩后 blob 的 sha256(同一管道算出)
- **`config.rootfs.diff_ids`**:截断到 moved 层数 + 追加新 diff_id
- **`config.history`**:截断到 moved 层数 + 追加 1 条新 history(`comment` / `created`;全空时 `empty_layer:true`)
- 移除 `container` / `container_config`,更新 `created`
- **image ID** = config JSON 的 sha256(ggcr 组装时保证 canonical 序列化)

用 ggcr 组装后不再需要 Python 那套"正则修剪微秒 / OrderedDict 保序"的字节对齐 hack —— 库自身保证 canonical。

### 3.6 输出与压缩(**性能核心管道**)

这是全案最贵的一步,决定端到端耗时。设计要点:

**a. 单遍并行压缩 + 内联双 hash** —— 合并 producer 产出的 tar 字节,一次流过 tee,同时:算未压缩 diff_id、送并行压缩器、对压缩输出算 digest,一遍完成,绝不二次扫描:

```
[合并 producer] ──tar字节──▶ tee ──▶ sha256 ─────────────▶ diff_id
                               └──▶ klauspost 并行压缩 ──▶ sha256 ──▶ digest
                                                        └──────────▶ blob 落盘/写 layout
```

**b. 压缩器不用 ggcr** —— ggcr 内置压缩是标准库单线程 gzip。合并层必须用 `klauspost/compress`:gzip 用 pgzip(block 级并行),zstd 用其并行 encoder,把这唯一的压缩任务打满所有核。

**c. 压缩与合并流水线重叠** —— producer(解压上游层 + 合并)与 consumer(压缩 + 写)分处不同 goroutine,用 `io.Pipe` 连接;墙钟 ≈ max(合并耗时, 压缩耗时),而非二者相加。

**d. move 层零压缩** —— 保留的下层直接透传原压缩 blob,不解压不重压(§4.2-A)。

**e. 算法/级别可选,默认偏快** —— 默认 zstd(吞吐与压缩比双优);`--compression=gzip` 兼容旧环境;`--compression=none` 跳过压缩(最快,产物大);`--compression-level` 默认取快档而非最高档。

**f. 输出格式** —— 默认 OCI layout(目录/tar),媒体类型随压缩选 `+gzip` / `+zstd`;`--format docker-archive` 兼容 `docker load`。

## 四、性能保证(耗时)

性能不能靠"感觉快",要先建立耗时模型、定位真实瓶颈,再按影响力排序施加杠杆,最后用基准 + 回归门禁把它"锁住"。

### 4.1 耗时模型:时间到底花在哪

Python 版慢在**管道**(全量落盘、逐字节过解释器、O(n²) 查找、结尾多次重复扫描),它其实**根本没做压缩**。Go 版一旦把管道做对,**真正的 CPU 大头会转移到压缩**。

设 squash 范围未压缩总量 = U,保留(move)层总量 = M,去重后写出量 = U'。各阶段成本:

| 阶段 | 成本量级 | 是否瓶颈 |
|---|---|---|
| move 层处理 | **可做到 ~0**(直接复用原 blob) | 否 |
| 解压 squash 输入层 | U / (~200MB/s·核),gzip 单流串行 | 中 |
| 合并拷贝字节 | U 内存拷贝(`io.Copy`) | 否(可忽略) |
| **压缩输出层** | U' / (gzip -6 约 30–50MB/s·核) | **是,主瓶颈** |
| 算 hash(diff_id/digest) | ~1GB/s(SHA-NI) | 否 |

**结论:多 GB 镜像里,输出层压缩是唯一的数量级瓶颈;其余阶段都能靠管道设计压到可忽略。** 性能保证 = 不重蹈 Python 管道覆辙 + 把压缩这个新大头压下去。

### 4.2 性能杠杆(按影响力排序)

**A. move 层零成本复用(最大杠杆)** —— 被保留的下层没有任何变化,**直接逐字节复制原 blob**(输出 OCI layout 时甚至可直接引用),不解压、不重压、不重算 hash,digest/diff_id 从源 manifest 照抄。Python 版却对每个 move 层重新扫描 + hash,是纯浪费。只有那 1 个 squash 输出层需要真正干活。

**B. 唯一的压缩任务并行化** —— 既然只压 1 层,就把它压满所有核:`klauspost/compress` 的 block 级并行 gzip(pgzip)或并行 zstd,C 核近似 C× 加速。这是把主瓶颈线性打下去的核心手段。

**C. zstd + 可调级别 + 快的默认值** ——
- `--compression=zstd` 比 gzip 快 3–5× 且压缩比更好,除非目标环境只认 gzip,否则作首选
- `--compression-level` 暴露给用户;默认取"快"档而非最高档(gzip -1 与 -9 是数量级差异)
- `--compression=none` 供"只求快 / 后续还要再处理"的场景

**D. 单遍流水线 + 内联 hash,杜绝重复 pass** —— 一条 `io.Pipe` 串起来,边合并边压边算两个 hash:

```
[合并 producer] ──tar字节──▶ tee ──▶ sha256(diff_id)
                               └──▶ 并行压缩 ──▶ sha256(digest) ──▶ blob
```

diff_id(未压缩 tar 的 sha256)与 digest(压缩 blob 的 sha256)在同一遍流里用 `io.MultiWriter` 同时算出,不像 Python 那样结尾再独立扫好几遍。

> **选库要注意的坑**:ggcr 的便捷构造器(`tarball.LayerFromOpener` 等)为了同时拿到 diff_id 和 digest,常见实现会**压两遍或落临时文件**,一旦如此,最贵的压缩阶段跑了两遍,直接慢近 2×。**输出层必须用 `stream.Layer` 或自己实现单遍 streaming 的 `v1.Layer`** 包住上面的管道,确保只压一遍。这是路线 A 用 ggcr 时最容易踩的性能陷阱。

**E. 零落盘 + map 去重** —— 层 tar 流直接进合并器,不做全量 extract-to-disk;去重/skip 用 map + 前缀树,消灭 O(files²)。这是"不重蹈 Python 覆辙"的底线。

**F. 阶段重叠(pipelining)** —— 解压下一层、合并当前层、压缩输出、写 blob 分属不同 goroutine,通过 pipe/channel 天然重叠;压缩在跑时,解压和合并同时喂数据,CPU 不空转。

**G. 输入解压的预取** —— gzip 单流不能并行解压,但合并是 newest-first 单遍、每层只解压一次;处理当前层时后台 goroutine 已在解压下一层,把串行解压的等待藏掉。

### 4.3 Python 瓶颈 → Go 方案对照

| Python 瓶颈 | Go 方案 |
|---|---|
| 全量 extract 到磁盘 | 层 tar 流直接进合并器,零落盘 |
| 逐字节过解释器拷贝 | `io.Copy` 内核级 |
| list 线性 skip 查找 O(n²) | map / 前缀树 O(1)~O(depth) |
| 结尾多次重打包 + 独立 hash pass | 单遍写出,`io.MultiWriter` 同时算 diff_id/digest |
| 无压缩 / 单线程 | `klauspost/compress` 并行 gzip/zstd |
| 对每个 move 层重新扫描 + hash | move 层直接复用原 blob,零成本 |
| 全程单线程 | errgroup 并行读层 / 预索引 / 阶段重叠 |

### 4.4 压缩耗时与"路线 A/B"无关 —— 别把性能寄托在选路线上

一个关键澄清:既然主瓶颈是**压缩**,而压缩在 A/B 里**都由我们自己的 `klauspost` 并行管道完成**(§3.6),那么**路线选择基本不影响压缩耗时**。ggcr 在 A 里只接收"已压好的 blob",不参与压缩。所以:

- **决定压缩耗时的是**:压缩器(klauspost vs 标准库)、算法(zstd vs gzip)、级别、并行核数、move 层是否复用。这些两条路线完全共享。
- **A 与 B 的差异只在冷路径**:manifest/config/layout 的组装与写盘,不在热路径上,占比极小。

因此性能上限对比化简为:

| | 路线 A(ggcr 组装) | 路线 B(全自研) |
|---|---|---|
| 压缩/合并热路径 | **自研并行管道,与 B 相同** | 自研并行管道 |
| 理论最优上限 | ≈ B(差距 <5%,仅冷路径抽象开销) | 最优 |
| 主要风险 | **误用 ggcr 默认压缩/hash** → 单线程 gzip 且可能压两遍,慢 2×+ | 格式正确性全自研,易出 bug |
| 达到最优的难度 | 中(绕开 ggcr 压缩,自己压好再交给它) | 高 |

> **红线**:路线 A 下**绝不能**用 `tarball.LayerFromOpener`/`mutate.Append` 让 ggcr 自己去压缩合并层——那会退回单线程 gzip,且为同时拿 diff_id 和 digest 可能压两遍,直接摧毁性能。正确做法是我们压好 blob、算好双 hash,用 `partial`/自实现的 `v1.Layer`(`Compressed()` 直接返回已压好的流、`Digest()`/`DiffID()` 返回已算好的值)交给 ggcr 组装。

**结论**:压缩耗时优先的目标下,选 A 还是 B **不改变性能天花板**;真正决定成败的是 §3.6 那条"自研并行压缩 + 内联双 hash + move 层复用 + 阶段重叠"的管道。因此**推荐 A**——性能等同 B,却省掉全部格式正确性风险。纯 B 只在后续要做 A 做不到的能力(跨层 chunk 级去重、内容寻址增量输出)时才值得。

### 4.5 压缩耗时量级估算(定预期)

以合并层未压缩 U' 计,C 核并行:

| 算法/级别 | 单核吞吐(约) | C 核估算(U'=2GB,C=8) |
|---|---|---|
| gzip -6(标准库,单线程) | 30–50 MB/s | **40–65s(ggcr 默认,禁用)** |
| pgzip -6(klauspost 并行) | 30–50 MB/s × C | 5–8s |
| zstd-3(klauspost 并行,**默认**) | 150–300 MB/s × C | **1–2s** |
| none | —— | ~0(仅 IO) |

数量级差异清楚说明:**压缩器/算法的选择,比路线选择重要一个数量级**。默认 zstd + 并行,把 2GB 合并层压缩从"几十秒"降到"个位数秒"。

### 4.6 怎么"保证"—— 靠测量与防回归

1. **首要指标 = 压缩耗时**:基准直接测"合并层压缩墙钟"这一项,单独 profile,确保它随核数近线性下降(验证并行真的生效、没退回单线程)
2. **定基准集**:小/中/大、多层/少层、大文件/海量小文件等真实镜像,先用 Python 版跑出 baseline
3. **定 SLO**:如"压缩阶段随核数近线性加速比 ≥0.7×C;端到端(zstd)比 Python 版快 ≥5×",写进基准断言
4. **`go test -bench` + pprof**:CPU profile 确认热点落在 `klauspost` 压缩而非 tar 管道或 ggcr 抽象;若发现 ggcr 在压缩,立即报警(踩了 §4.4 红线)
5. **CI 回归门禁**:基准跑在 CI,回退超阈值(如 >15%)即 fail
6. **分档验证**:none / gzip / zstd 三档分别测,让用户按"要快还是要小"选择

**预期:默认 zstd + 并行下,压缩阶段较标准库单线程 gzip 快 5–15×;端到端远快于 Python 版。**
